# Known Issues and Risk Register

| ID | Risk / issue | Impact | Mitigation | Status |
|---|---|---|---|---|
| K-001 | RN 0.88.1 requires current native toolchain | Build blocked | Audit machine before scaffold; preserve generated versions | Open |
| K-002 | iOS 27 simulator runtime may not be installed | Cannot verify target iOS | Check Xcode runtimes and install if available | Open |
| K-003 | Android 15 API 35 is not the same as compile SDK 37 | Build config confusion | Use API 35 emulator, generated compile/target SDK | Open |
| K-004 | Platform geofence capacity | Some reminders not monitored | iOS 20 regions; Android 100 per app per device user; priority-based registration | Open |
| K-005 | Background location behavior differs by OS/vendor | Missed/delayed triggers | Real-device matrix and explicit limitations | Open |
| K-006 | Map SDK compatibility with RN New Architecture | Native build risk | Defer and run minimal two-platform spike | Open |
| K-007 | Fixed production radius and domain validation must stay aligned | Invalid saved data | Production radius is fixed at 200m; Developer Mode may override only in Debug | Open |
| K-008 | Public Nominatim has usage limits | Search may be throttled | Online-only, explicit user action, no autocomplete spam | Open |
| K-009 | Notifee version/platform behavior needs validation | Notification delivery risk | Test local notification separately before geofence | Open |
| K-010 | Background speed/location samples may be sparse or inaccurate | Arrival confirmation delayed or false-positive risk | Require valid samples, explicit sample-gap policy, and physical-device testing | Open |
| K-011 | Developer flag could accidentally leak into Release | Test-only behavior exposed in production | Native Release hard-disable plus `__DEV__` guard and release verification | Open |
| K-012 | Overflow Complete/Delete from card do not persist state (mock only) | No real completion/deletion on mock data | Resolved in Phase 4: store.save() and store.deleteById() wired in HomeScreen overflow actions | Resolved (Phase 4) |
| K-013 | CreateReminder form does not persist data (mock only) | Save navigates back but no reminder stored | Resolved in Phase 4: store.save() wired in CreateReminderScreen; DRAFT auto-activation added | Resolved (Phase 4) |
| K-014 | Xcode 26.3 Swift toolchain: _DarwinFoundation module not found (iOS build always fails) | Cannot build or test iOS on this machine | Requires Xcode update/reinstall or Swift module cache repair. Does NOT block Android builds or TypeScript compilation. Verified: original project (without SpikeModule) fails identically. | Open |
| K-015 | Android Geofencing API (v21.x): `getGeofenceTransition()` returns single int, no `triggeringLocation` property — use `getTriggeringLocation()` method | API mismatch if using newer docs | Used singular `getGeofenceTransition()` and `getTriggeringLocation()` throughout. No functional impact — single-transition handling is sufficient. | Documented (Task 8.3) |
| K-016 | Stationary reading persistence is best-effort — if store fails, crash-safety recovery is lost (but normal operation continues) | No crash-safety data on failure | Graceful degradation: stationaryService continues working, only crash-recovery is affected. | Documented (Task 8.10) |
| K-017 | Relative-time testing on a real device (on the road and at work, 8 h stationary) showed statuses that were hours out of date and no arrival notification. Root causes: (a) Android geofence transitions were dropped when the React context was null, because `GeofenceEventReceiver` returned early with no persistence; (b) DWELL transitions were never requested (`setTransitionTypes` missing) and would have been routed to `geofenceExit`; (c) the crash-safety columns `lastStationaryReadingAt/Lat/Lon` were never created, so `updateStationaryReading()` threw and was swallowed; (d) `resumeStationaryTimer()` never restored accumulated time and never started sampling; (e) `WAITING_FOR_EXIT` reminders were never registered natively, so no EXIT could ever arrive; (f) stationary speed used wall-clock time between JS calls instead of fix timestamps; (g) `distanceFilter: 5` suppressed fixes for a stationary user; (h) background location was never requested, which is mandatory for background geofencing on Android 10+. | Arrivals detected hours late or not at all | Fixed in v1.1.0: native event persistence + drain, DWELL transitions with 120 s loitering delay, native arrival notification with cached copy, schema v2 migration, corrected resume path, fix-timestamp speed, continuous fixes, background-location onboarding and Settings row, resume reconciliation against the current position. | Resolved (v1.1.0) |
| K-018 | iOS has no equivalent persistence layer: `didEnterRegion`/`didExitRegion` emit to JS only. If iOS relaunches the app in the background for a region event and the bridge is not ready, the transition is lost the same way the Android path used to be. Not fixed in v1.1.0 (no iOS toolchain on the build machine — see K-014). | Delayed or missed iOS arrivals | Apply the same pattern: persist transitions in `UserDefaults` inside `GeofencingManager` and drain from JS on start/resume. | Open |
| K-019 | A native DWELL notification is posted by the receiver and the JS layer deliberately does not post a second one. If `POST_NOTIFICATIONS` is revoked, arrival still moves the reminder to TRIGGERED without an alert; the in-app list shows the new state. | Silent arrival when notifications are blocked | Settings shows notification permission state; the diagnostics log records the skipped notification. | Documented (v1.1.0) |
